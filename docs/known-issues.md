# 已知问题与待改进

这份文档记录当前代码里**已知**的问题、取舍和待办。分两类：

- **问题**：现在的行为不对，或者和它的目标不符。
- **取舍**：现在的行为是有意选的，但代价要知道。改不改是判断题，不是修 bug。

每条都写了「为什么重要」和「怎么修」。严重程度是我自己排的，不是客观标准。

---

## 零、安全模型（读其它条之前先看这个）

真正提供保护的是**三处**，其余都是降低概率：

1. **文件工具的路径闸门**（`tools/safety.py` + `tools/files.py`）：围栏、符号链接、敏感路径、读-before-写、改前备份。防的是"模型手滑或跑偏，破坏了它不了解的东西"。
2. **bash 的 docker 沙箱**（`tools/shell.py`）：只读根、无网络、只有项目目录可写、跑完就删。防的是"命令碰到宿主机"。
3. **权限模式的用户确认**（`permissions.py` + `prompting.py`）：四档（`default` / `accept edits` / `plan` / `bypass permissions`），改文件的调用和 bash 都按档位放行 / 询问 / 拒绝。防的是"模型跑偏的时候用户没在看"。

第 3 条和前两条不是一类：它是**人看的**，所以有多硬取决于你有没有真的在读那条提示——`accept edits` 档下它对改文件一点都不拦，`default` 档下用户随手敲个 y 就等于放行。它不是自动边界。而且四档里有一档是**把它自己整个关掉**的：`bypass permissions` 什么都不问，那一档下就只剩前两条（见 F4）。

**除此之外的一切——命令风险分类（还没做）、输出的关键词涂黑——都是启发式**，只降低概率，不构成保证。别把它们当边界：一个不含任何关键词的密钥、一条换种写法的危险命令，都能绕过去。

## 一、bash / 命令执行

### A1. bash 能改项目里的任何文件，绕过文件工具的全部闸门 —— 严重

**现在的行为**（实测确认）：

```
$ bash: echo 'KEY=clobbered' > /workspace/.env
磁盘上现在是: b'KEY=clobbered\n'
```

`/workspace` 是项目目录的挂载，**可写**（这是必要的——agent 要改代码）。于是只要 `--shell` 一开：

- **敏感路径闸门失效**：`read_file` 读不了 `.env`，但 `bash` 能覆盖它。
- **读-before-写失效**：模型没读过 `.env`，照样能整个盖掉。
- **备份失效**：`.agent/.history/` 里不会留下这次的旧内容——因为根本没过 `_commit_change`。
- 同理 `.git/hooks/pre-commit` 也能造出来（那个 `write_file` 已经拦了的东西）。

**为什么重要**：前面这一整套文件闸门，是为"改文件"这条路径建的；bash 一开，就多了一条**平行的、不受管的**改文件路径。这是目前安全模型里最大的一处不交叉。

**怎么修**：几条路，都不便宜——
- 把挂载改成只读，让"改文件"只能走文件工具（但 agent 就跑不了 `pytest` 写缓存、也跑不了任何会写盘的工具，实用性大打折扣）。
- bash 执行前把项目目录快照一份，跑完比对、把没经过文件工具就改掉的东西还原（贵，且难以判断"该不该还原"）。
- 接受它，但在文档和界面上说清楚：**开了 `--shell` 就等于放弃了文件工具那一层保护**。
- 折中：只把**敏感路径**单独挂成只读（Docker 不支持按文件挂，得改目录结构）。

### A2. 挂载把 `.env`、`.git/config`、`.agent/.history` 摆进了容器 —— 高

**现在的行为**：挂载是整个项目目录，里面就有这三样。容器里的命令 `cat .env` 就能拿到密钥。

**为什么重要**：`--network none` 挡不住这条——泄露路径是**工具的返回值进模型上下文**，然后随下一轮对话发给模型服务商，跟网络无关。

后两样更隐蔽：`.git/config` 的 remote URL 里常嵌着 token；`.agent/.history/` 存的是改动前的旧副本，可能含着**已经被删掉的**密钥（比如某个文件在被清掉敏感内容之前的样子）。

**怎么修**：涂黑（A3）只挡住"被打印出来"，挡不住"被读到"。真正的修法是让容器看不到这些路径——Docker 的 bind mount 不支持按文件排除，只能改成"挂上层 + 逐个挂子目录"，或者在容器启动前做一次只读的过滤视图。

### A3. 输出涂黑是启发式，不是保证 —— 中（需要正确认知）

**现在的行为**：命令输出里，凡是含 `api` / `token` / `secret` / `password` / `bearer` / `sk-` / `ghp_` 等词的行，整行换成 `[已涂黑]`。

它挡住了最常见的那一条（`cat .env`，因为 `DEEPSEEK_API_KEY` 含 "api"）。但：

- 一个不含任何关键词的密钥照样漏——一串裸的十六进制、一个自定义的变量名（`FOO=...`）都拦不住。
- 反过来会误伤：README 里提一句 "API 地址" 也会被整行涂掉。

**为什么重要**：有人看到"输出被涂黑了"会以为安全了。它不是边界，是降低概率。

**怎么修**：想更强的话可以加"高熵字符串"启发式（长且随机的串），但会带来新的误伤。**更该做的是 A2**——让容器压根够不着那些文件，这一层就不用背这个责任。

### A4. 没有 `--ulimit`，挂载目录没有写入上限 —— 中

**现在的行为**：`/tmp` 是限了 256m 的 tmpfs，根文件系统只读。但**挂载的项目目录是宿主机磁盘，没有任何上限**。

**为什么重要**：一条 `dd if=/dev/zero of=/workspace/big bs=1M count=100000` 能把你的盘写满。`--pids-limit` 和 `--memory` 管的是容器自己的资源，管不到挂载。

**怎么修**：`--ulimit fsize=<字节>` 能限制单个文件的大小（挡得住上面那条，挡不住"写一万个小文件"）。彻底的办法是给项目目录单独划一个配额卷，代价是项目不再直接落回宿主机。

### A5. 进程被强杀时不会清理遗留容器 —— 中

**现在的行为**：正常退出靠 `--rm`；超时路径靠 `--cidfile` + `docker rm -f`（实测过：只杀 docker 客户端，容器不会停）。但**agent 自己被 Ctrl+C 或被 kill 时**，那条清理路径不会执行，容器会留着继续跑。

**为什么重要**：留下的容器占着内存、pids、内存限制那 2g，还挂着你的项目目录。

**怎么修**：启动时扫一遍 `docker ps --filter name=mca-`，把归属自己的（比如超过 N 分钟、或者按标签 `--label mca=1`）清掉。顺带：给容器打 `--label` 比按名字前缀匹配可靠。

### A6. `--name` 冲突没有重试 —— 低

名字是 `mca-` + uuid4 前 10 位，撞车概率极低。但如果恰好撞上（或者上一次的残留还占着这个名字），`docker run` 会直接以 125 失败，被报成"容器没起来"。

**怎么修**：捕获这种情况换一个名字重试一次。优先级低。

### A7. 容器内挂载的属主在 Windows 上形同虚设 —— 低（需要正确认知）

**实测**：挂载进来的文件在容器里显示成 `-rwxrwxrwx root root`——Docker Desktop 的 Windows 文件系统把所有文件摊成 777。所以 `--user 1000:1000` 对**挂载内容**不起任何限制作用（对容器内的 `/` 仍然有效）。

**为什么重要**：别以为 uid 能挡住容器改你的文件。它挡不住。

## 二、文件读写工具

### B1. 陈旧检测只用 mtime —— 已修 2026-10-10

**当时的行为**：`_commit_change` 只比 mtime，`ReadFileState` 里存的第二个值（当时的字符数）从加上到那时一次都没被读过。

**为什么重要**：整道闸门只有一个信号。内容变了而 mtime 没动时，守卫会认为"没变化"→ 放行 → 把一份模型从没看过的内容静默盖掉，正是它要防的那件事。

当时判断这个洞**只**取决于文件系统的时间戳精度，NTFS 100 纳秒，所以"几乎不可能——两次写隔了毫秒级"。**这个判断是错的**：名义精度不等于时间戳取值有多粗。实测这台机器（NTFS）上，两次写同一个文件、时间戳是否一样：

| 两次写之间隔 | mtime 没变的概率 |
| --- | --- |
| 0 ms | 77% |
| 1 ms | 60% |
| 3 ms | 34% |
| 5 ms | 19% |
| ≥ 10 ms | 0%（6000 次里一次没有） |

**有效的撞车窗口大约 10 毫秒**，毫秒级恰恰撞得最多，而不是"隔了毫秒就安全"。用真实工具跑 `read_file → edit_file → replace_lines`，30 轮里 9 轮 `edit_file` 之后 mtime 没动、3 轮 `replace_lines` 之后的 mtime 和上一次完全相同（内容确实变了）。FAT / U 盘（2 秒）、网络盘那些更粗的只会更糟。

**怎么修的**：记的值从"字符数"改成**字节数**，`_commit_change` 一次 `stat` 同时取 mtime 和 `st_size`，两个一起比。零额外成本；长度变了就一定拦得住，跟时钟精度无关。`read_file` 里"读的过程中被改过了"那道检查同样加了长度信号（比 `len(data)` 和现在的 `st_size`）。

**还剩的洞**：两个信号都一样的改动照样漏——长度不变、时间戳又恰好撞在同一个刻度里（`alpha` → `ALPHA` 就是）。要堵它得存内容摘要（每次读多算一次哈希），现在没做。

### B2. `read_file` 不返回行号，`replace_lines` 用起来别扭 —— 已修 2026-10-13

**当时的行为**：`read_file` 输出的是纯内容，而 `replace_lines` 要的是行号。

**为什么重要**：模型得自己数行——**而且每次编辑都会改变总行数**。做一个多步修改时它很容易数错。这个工具存在的意义就是"按位置改"，行号难拿就等于白给。

**怎么修的**：每行前面带上它在**文件里**的真实行号（`12 | 正文`，宽度按最后一行对齐）。三点值得记：

- **行号是文件里的位置，不是 1..N。** 只读一段时这两个数不一样，而 `replace_lines` 要的正是前者——所以编号发生在切片之后。
- **先编号、再截断**（不是反过来）。行号从此是正文的一部分，跟着一起受 `MAX_READ_FILE_CHARS` 管着：总数守在限额以内，代价是同样长的文件现在少给几行。反过来（先截再编号）会超出限额，超多少取决于文件有多少行，那就没边了。
- **"文件共 N 行"那句接在截断之后。** 它是元信息，不该带行号，也不该被截断吃掉——修之前它拼在正文里，长文件一截就把它一起吞了（这次顺带修掉）。

**新增的失败模式，以及配套**：模型可能连着行号一起抄进 `edit_file` 的 `old_string`，那就一定匹配不上。所以 `edit_file` 的描述里明说了这件事，`read_file` 的描述里也点明"行号不是文件内容的一部分"——得在它咬人的地方提醒，光加功能不够。

### B3. CRLF 文件编辑后混行尾 —— 低

**现在的行为**：`new_text` / `content` 里补的是 `\n`（`write_file` 用了 `newline=""`，不做转换），而文件原有的行保留自己的 `\r\n`。

**为什么重要**：`.gitattributes` 里是 `* text=auto`，git 提交时会归一化，所以不至于乱；但工作区里会混，`git diff` 看起来会怪。

**怎么修**：看插入点相邻那行是什么结尾，跟着用同一种。

### B4~B7. 有意选的取舍（不是问题，但要知道）

- **B4. 改已有的文件必须先读过。** `write_file` / `edit_file` / `replace_lines` 都要求 `read_state` 里有记录。新建文件不需要。这是"读-before-写"的本意，代价是模型改任何东西之前都得先 `read_file` 一次。
- **B5. `write_file` 不会替你建父目录。** 上级目录不存在就报错。选这个是因为路径写错多半说明模型搞错了位置，替它建一棵目录树更糟。
- **B6. `replace_lines` 的 `end_line = start_line - 1` 表示空区间（纯插入）。** 这是为了让"在文件头尾插内容"不用重抄相邻那一行。语义是自定义的，schema 里写了。
- **B7. `edit_file` 多命中时默认只换第一处**，并在返回里注明原本有几处。风险是模型可能想改的是另一处；但现在它至少知道漏了几处。
- **B8. 敏感判定看的是路径和文件名，不是内容。** 一个叫 `config.txt` 的文件里放着密钥，`is_sensitive` 拦不住。要在内容层面兜，得靠扫描文件内容（贵），或者靠 bash 输出那层的涂黑（那是另一个层面，见 A3）。

## 三、搜索工具

### C1. `project_tree` / `glob` 先建全树再剪枝 —— 低

`max_nodes` / 输出截断限制的是**输出量**，不是**工作量**：树是造完（到 `max_depth` 层）之后才挑节点的。跳过规则挡掉了 `.venv`、`node_modules` 这些大头，剩下的源码树通常很快，所以先这样。

真要在超大仓库上把工作量也限住，得改成边走边数——代码会复杂不少。

### C2. `grep` 的 ripgrep 分支只有假进程测过，而那一段现在开始走了 —— 中

**前提变了（2026-10-13 核）**：这台机器上**装了真 ripgrep**——`shutil.which("rg")` 指向 winget 装的 15.2.0，不再是 None。原来那条"装了再验"的拦路理由没有了。

**而后果比原来更重，不是更轻。** `files.py:759` 是 `exe = shutil.which("rg")`：

- 以前它返回 None，rg 那条支路（参数拼装、输出解析、结果过滤）**永远走不到**，每次都落兜底——没验过的代码是**死的**，最坏也就是兜底慢一点。
- 现在它会走。也就是说**那段没验过的代码从今天起是活的**：rg 拿到这些参数到底怎么表现、解析对不对，直接决定 grep 工具眼下好不好用。

**另外那句告诫也过期了**：以前 Git Bash 里 `rg` 可能是 Claude Code 注入的同名函数、不是真 ripgrep，用它验证会误导；现在这台机器上 `type rg` 指向的就是 winget 那个真货。（换台机器还是可能撞上——要验就用 `shutil.which("rg")` 找到的绝对路径。）

**怎么修**：现在没有拦路了，跑一遍对照就行——拿真 rg 的输出跟兜底那条路对比，看路径归一化、退出码 2、敏感文件过滤这几处对不对得上。

### C3. `truncate_text` 可能切在一行中间 —— 低

按字符数硬切，树形输出被截断时会留半截 `│   ├── xxx`。改成按整行切会好看些。

## 四、agent 与 CLI

### D1. 交互模式没有记忆 —— 已修 2026-10-12

**当时的行为**：CLI 的交互循环每轮都是 `runagent(line, ...)`——**一次全新的调用**，把用户这一行当作唯一的输入。上一轮说了什么，模型完全不知道。界面看起来像聊天，实际是"一问一答、互不相干"。

**怎么修的**：`854c449` 把交互循环抽成 `_chat(...)`，上一轮的 `AgentResult.messages` 接下去当这一轮的输入（现在这份历史活在 `ChatState.messages` 里，见 commands 那一摊）；provider 也挪到循环外只建一次，不再每轮重建 HTTP 客户端。

### D2. 没有默认的 system prompt —— 已修 2026-10-12

**当时的行为**：`runagent` 的 `system` 是可选的，CLI 从不传。于是模型没有任何"你是个 coding agent、工具该怎么用、改文件之前要先读"之类的交代，全靠工具描述本身暗示。

**怎么修的**：同一笔（`854c449`）加了 `system_prompt.py`，CLI 每次运行都传一份。后来 `164d171` 又从"循环外建一次"改成**每轮重拼**——因为记忆和 `AGENTS.md` 都可能中途变，拼一次用到底的话，这一轮 `remember` 的东西要重启进程才看得见。

**这两条的账要记一下**：D1 和 D2 是同一笔提交修的，而那次改动**没有回头更新这份文档**——于是两条已经不存在的问题又在这儿挂了一天，其中一条还标着"中高"。危害不在于占地方，在于**下一个人会照着一个已经不存在的问题去做决定**（比如"记忆要重做一遍"）。修东西的时候顺手销账，比事后回来考古便宜。

### D3. `trace` 现在是字符串，没法程序化区分事件 —— 取舍

按你的要求，trace 里放的是渲染好的文本（`→ 调用` / `← 结果` / 最终回答）。好处是拿起来就能打印；代价是想在代码里区分"这条是调用还是结果"只能靠前缀。

### D4. 输出被截断时 provider 自己抬 max_tokens，但抬到顶还是截断就没人管了 —— 取舍

**现在的行为**：`max_tokens` 默认才 1024，一个长回答或一次 `write_file` 很容易不够——而截断出来的文本照样是个非空的最终回答，**没人看得出来它被切过**。所以 `AnthropicProvider.create()` 撞上 `stop_reason == "max_tokens"` 时会**静默**抬到 16384 再发一次（实测这个端点收 16384；再往上 65536 起 SDK 自己就拒绝非流式请求了，所以再高不是改数字的事，得改成流式）。

**两条有意定下来的**：

- **直接跳到天花板，不做阶梯**。`max_tokens` 是**上限不是目标**——写大了不额外花钱（只按真正生成的那些计费），所以第一次就跳到能要到的最大值，比 1024/2048/4096 一级一级爬便宜得多：爬的每一级都要为一次马上会被丢掉的生成付钱。而且只重试一次，循环天生有界。
- **放在 provider 里、不往 agent 递**：这是"这次请求向模型要多少生成空间"的事，不是对话的事（agent 手上只有归一化之后的 ModelResponse，本来也看不见）。顺带保住了 Provider 协议一行不动，别的后端想各自实现也行。抬上去也**不记在实例上**——那是对一次意外截断的修补，不是新配置；每轮都撞说明默认值该抬了，那是人该做的决定。

**还剩什么**：抬到天花板**还是**被切的话，那份截断的回答就原样交回上层——而 `stop_reason` **目前没有任何地方读**（全项目只有 provider 在写它）。所以那一下仍然是静默的：用户拿到半截回答，看不出异常。这就是"升级失败 → 恢复式重试"那条缺口，和"提示词过长"一样属于还没做的反应式错误处理。

### D5. 工具结果折叠 —— 删过又回来了，但只在冷点折（2026-10-16）

**现在的行为**：`folding.fold_stale` 把最近 5 条以外的工具结果换成"开头 200 字符 + 一句
说明"。**只在缓存大概已经冷了的时候做**——判据是会话文件的 mtime（每轮结束都 `append` 一次，
所以它等于"上一轮什么时候结束的"）距今超过 `FOLD_AFTER_SECONDS`（10 分钟）。

**只有标了 `Tool.foldable` 的工具的结果进候选**，而且那"最近 5 条"数的也是**候选**里的——
不可折的那些既不占名额、也不会被动（Claude Code 的 `keepRecent` 就是这么数的）：

| 能折 | 不许折 |
| --- | --- |
| `read_file`、`grep`、`glob`、`list_files`、`web_search`、`web_fetch`、`bash` | `agent`、`project_tree`、`read_memory`、`read_skill`、`read_skill_file`、`read_tool_result` |

判据分两层。**能折的**是"又大、而且折掉之后不至于真丢"：`read_file` / `grep` / `glob` /
`list_files` 重跑一次就能拿回来；`bash` / `web_fetch` / `web_search` 重跑不等价（命令有副作
用、网页会变、搜索花钱还会漂），所以它们标了 `Tool.fold_persist`——**折之前先按 `tool_use_id`
落一份到 `.agent/tool-results/<会话 id>/`**，上下文里只留开头 200 字符加上路径和 id，模型要用
时用 `read_tool_result` 取。写不成就不折这一条：宁可让它继续占着上下文，也不能给模型一个指向
空处的引用。右边那一列是**结论和方向**——子 agent 交回来的方案就是"方向"本身（它背后是一整趟
子 agent，重跑一遍是几分钟和几毛钱），项目概览是"我现在在哪儿"的参照，记忆/技能/落盘原文都是
模型**特意去取**回来的。

**默认 `False`（不折）落在安全的那一侧**：新加一个工具忘了标，后果是"少省一点"，不是"它的
结论被折没了"。名单由注册表现算（`ToolRegistry.foldable_names()` / `fold_persist_names()`），
所以 CLI 另外注入的 `agent` / `ask_user` 自动落在外面，不必在折叠那边另写一份"这些不许折"。

**没有手动入口**，这是有意的：它划不划算完全取决于"缓存冷不冷"，而那件事用户看不见（我们
自己也只能靠文件 mtime 猜）。让人敲一条命令去赌，赌错了就是多付一次全价——而真嫌上下文长的
时候，该敲的是 `/compact`。

它**不花钱**：只换内存里那份历史的内容，会话文件里原文一个字不动（接上会话拿回来的还是完整
的那份）。唯一会碰盘的是 `fold_persist` 那三类——那是把正文**另存一份**，不动会话文件。判据
只有"冷不冷"，**不看大小**——下面那笔账说的就是为什么。

**为什么 2026-10-15 删过它**：那时候的 `trimming.py` 是**每一步**都重算一份视图——每多一条
新结果，就有一条滑出"最近 8 条"的窗口，于是**每一发请求**的前缀都在中间被改动。而这个端点
的缓存以**整个请求**为单位匹配：

| 请求 | 载荷 | 原价 token | 命中 token |
| --- | --- | --- | --- |
| 一模一样再发一遍 | 44,165 字符 | 134 | 18,429 |
| **只往后追加**一条新的工具结果 | 46,926 字符 | 1,088 | **18,560** |
| **折掉一条旧的**之后再加一条 | 23,841 字符 | **9,049** | **384** |

**载荷小了一半，命中从 18,560 掉到 384，这一步贵了 6 倍。** 省下的是那几条旧结果本来在缓存里的价（deepseek-flash 的命中价是未命中的 **1/50**，v4-pro 是 1/30），赔进去的是后面一大段按原价重算。而它**每一步**都要折一条——每多一条新结果，就有一条滑出"最近 8 条"的窗口。

官方文档印证（`api-docs.deepseek.com/guides/kv_cache`）：缓存单元在**请求边界**落盘，"a subsequent request can only hit the cache if it **fully matches** a cache prefix unit"。所以不是"从分歧点往后失效"，是**要么整段中，要么几乎全不中**。

**它唯一划算的场合是缓存本来就是冷的**——当时这句结论本身就是出路。所以 2026-10-16 它按这个
前提回来了：老机制坏在"**每一步**都付一次重建的价"，新机制只在**真的冷**的时候付，而那时候
本来就要重建。设上下文 C、折完剩 αC：

- **冷的时候折**：那一发从 `C × 原价` 变成 `αC × 原价`，直接省 `(1−α)C`；之后每一发再省
  `(1−α)C / 50`（命中价是原价的 1/50）。**哪怕只有这一发，也是赚的。**
- **热的时候折**：那一发本来只要 `C/50`，现在要 `αC`——亏，而且要之后约 50 发才回本。

**三条硬约束**（踩了就出问题，测试各有一条守着）：

1. **只换 `content`，消息条数和块数一条不变。** 条数一变，`Session.record_summary` 的文件
   下标换算就错——它假设内存里的下标和文件里的消息行一一对应。
2. **不往会话文件里写新行。** `load()` / `_has_messages` / `_describe` 都是"`type` 不是
   meta/summary 就当 message"——加一种新行会在三处一起出错。折叠只往 `.agent/tool-results/`
   写独立文件，正好避开。
3. **返回新的一份，不改传进来那份。** 消息 dict 和它里面的块列表在别处是共享引用
   （`runagent` 只复制最外层那个列表），就地改会连调用方手里那份一起改掉。

**和压缩怎么分**：自动那条路上**折叠排在压缩前面**——折不要钱、压要一次模型调用，折完可能
就用不到压那一步。压缩是**有记录**的那一个（`record_summary` 往盘上记一笔，用户该看得见）；
折叠重算不要钱，所以不记。

**还剩什么**：

- **`FOLD_AFTER_SECONDS`（10 分钟）是个猜。** 要变成有依据的数得量这个端点的缓存 TTL：
  造一段内容、隔 T 分钟发一次、看 `cache_read_input_tokens` 什么时候掉到 0。好在猜错的代价
  是对称的（α = 0.5 时，折对省 0.5C、折错亏 0.5C），所以**只要"真冷"的概率过半就是赚的**
  ——阈值宽松一点没关系。但那个概率没人量过，**而且它必须比缓存 TTL 长**：短到那个数以下，
  折叠就会在缓存还热着的时候动手，那正是下面那张表说的贵 6 倍的场景。
- **`HEAD_CHARS`（200）和 `MIN_FOLD_CHARS`（400）也是拍的**，好在曲线很平。幂等现在由一条
  显式的闸保证：`_fold` 拼完说明之后，只要结果超过 `MIN_FOLD_CHARS`（或者不比原文短）就不折
  ——说明里现在带着路径和 id，已经不能假设"它一定短"了。
- **省下来多少取决于有多少条旧结果**：8 条时缩到 65%，30 条时能缩到两成左右。会话短的时候
  它几乎不起作用——它本来就是给长会话准备的。
- **子 agent 的结论现在保住了，但"方向"仍然只活在历史里。** Claude Code 那边方向不靠任何
  一条消息活着——任务列表存在盘上、每 ≥10 轮以一条 `<system-reminder>` 重新注入，连"计划"
  都是压缩之后专门恢复的一项。我们这儿没有那条通道：`plan` 子 agent 交回来的方案就是一条
  `tool_result`，不折它只是让它"暂时安全"——真到了非压不可的时候（`/compact`，或者哪天窗口
  吃紧），它照样会被摘要吃掉。要不要给这里也来一个独立的"计划工件"，是另一摊。

**"只追加"仍然是硬性要求**（`agent.py` 的 `send` 里写明了，`tests/test_agent.py::test_each_request_only_appends_to_the_previous_one` 守着它）——折叠和压缩都发生在**两次 `runagent` 调用之间**，所以那条守的是"**一次调用内部**别再加变换"。真往中间加一层，账单上看不出来。

**顺带修好的一处**：以前 `cut_point()` 数的是"没折过的那份历史"，和真正发出去的对不上，压缩因此触发得偏早（这个缝在 `MAX_READ_FILE_CHARS` 调到 50000 之后更明显）。折叠一删，两个数合成一个。

**还留着什么**：能让历史变短的动作现在有两个——折叠（只在冷点、免费；能重跑的原文在项目里，
拿不回来的那三类另存一份）和压缩（随时、要一次模型调用、落盘有记录）。自动压缩在这个端点上
基本不会触发（阈值 84 万，见 D8），所以真在管这件事的实际上是折叠和手动 `/compact`。

### D6. 会话只能一个个删，没有批量或按时间的清理 —— 低

**现在的行为**：`mca --delete <id>` 删一次一个——删之前先把要删的那次摆出来（多少条消息、最后说了什么）问一遍，`--yes` 跳过那一次问答。除此之外没有别的出口：`.agent/sessions/` 里那些"启动过但没说过话"的残骸、几个月前的老会话，都得自己一条条点名。

**为什么重要**：这一条现在不只是磁盘卫生——**删会话是"清理落盘的工具结果"唯一的出口**（见 G2）。落盘文件按会话分目录，`--delete` 一起端掉；没有别的动作能让它们走。

**为什么是先摆后问**：id 是一串数字加后缀，光看它认不出是哪一回；而会话文件是那次对话唯一的记录——没有回收站，也不像改文件那样有 `.agent/.history` 兜着（`Session.append` 是纯追加，从来不备份）。所以删之前要把"最后说的那句话"摆出来让人确认。

**怎么修**：两条不冲突的做法——`--list` 里那些"没说过话的"给个一次清掉的口子（它们从来没被列出来过，也永远接不上）；再给个按时间的（启动时删掉 N 天前的，或者 `--delete --older-than 30d`）。但**别做成启动时自动删**：那等于让一条你从没同意过的规则在背后删你的东西。要删就明说。

### D7. 会话 id 里多了一截随机 —— 取舍

**现在的行为**：id 从 `20261014-153000` 变成 `20261014-153000-0001a3f2`——时间戳后面跟一截"四位进程内计数器 + 四位随机"。

**为什么要它**：id 得在 `start()` 那一刻就定死，之后不能再改。落了盘的工具结果将来要按它分目录（见 G2），跑到一半改名会把一次会话劈成两处；而时间戳只精确到秒，同秒开两次就会撞上，以前的处置是**等真写盘的时候**往后排（`_free_path` 加 `-1`）——那正好是"跑到一半改名字"。

两截各管一件事：计数器保证**同一个进程里后开的排得更靠后**（`latest()` 按 id 字符串排，`--continue` 说"最近一次"靠的就是它）；4 位随机保证**两个进程同秒也不撞**。

**还剩什么**：

- **"不撞"是概率上的，不是保证。** 跨进程、同一秒、计数器又一样、随机那 4 位还撞了，概率约 1/65536。真撞上还是走 `_free_path`：改一次名字（那次会话的落盘目录会跟着劈开，认了），也绝不覆盖别人的文件。要彻底堵死得在 `start()` 就真去占名字（把文件建出来），而那会把刚修掉的"空会话文件"请回来。
- **跨进程同秒的次序是任意的**：两个进程在同一秒里各开一个，谁新谁旧由随机那截决定，`latest()` 取到哪个是随机的。同进程不受影响。要连这个都定死，得让 `latest()` 改看文件的写入时间而不是 id 字符串——那是另一件事，没做。
- id 长了一截，用户要敲或粘贴的字符串更长（`--resume` / `--delete`）。列表里能直接复制，代价不大。

### D8. 压缩阈值从"字符数"换成"占窗口的 80%" —— 2026-10-15

**改之前**：`MAX_HISTORY_CHARS = 200_000`，数的是 messages 的字符数。两个毛病：**量错了东西**（窗口吃的是 token，而且算上工具表和系统提示词，字符数两样都漏），以及**是个拍出来的数**——注释写着"12 万字符"而常量是 20 万，调过一次、理由没跟着改。

**现在**：看**上一发请求报回来的输入总量**（`input_tokens + cache_read + cache_creation`，三个不重叠的字段相加）占**模型上下文窗口**的比例，到 **80%**（`summarizing.COMPACT_AT`）就压。窗口按模型 id 查 `context_window.py` 那张表（查不到的按 40 万算）。手动 `/compact` 照旧，保留最近 6 轮照旧。

几个记账上的细节，都是推演过才定下的：

- **分子是三个字段相加，不是 `input_tokens` 一个字段。** 后者是"没走缓存的那部分"，缓存命中时只有几百（实测 1,088 对 19,648）——拿它判，阈值永远够不到。
- **锚点得成对**：`tokens` 是那一发的输入总量，`covered` 是**那一发请求里装了多少条 messages**。`covered` 不能拿 `AgentResult.messages` 的长度去顶——那份比发出去的长，响应是先拿到的、assistant 那条是之后才 append 的。
- **只认"带工具的最后一发"**（`ContextAnchor`）。用满步数时最后那一发是不带 tools 的收尾请求，少了整段工具 schema（占前缀一多半），拿它当锚点会系统性少算。
- **压过之后锚点必须作废**（`ChatState.forget_context`）。不作废的话下一轮会以为还是压缩前那么大：够阈值、又刚好攒够 7 轮，就再压一次——阈值被架空成"每 7 轮压一次"。
- **没有锚点时**（会话第一轮、`--resume` 上来还没发过请求）整段按字符粗估，系数取 2 字符 1 token（估大了早压、估小了晚压，早压更安全）。

**一个要提前知道的后果**：这个端点的窗口是 1,048,576，80% ≈ 84 万 token，而实测过 97 万 token 都能正常发出去。所以**在现在这个端点上，自动压缩基本不会触发**——它成了一条"防发不出去"的安全网，真正会让历史变短的动作只剩 `/compact`。

代价跟着来：历史会一直长到那个量级，而每一步都要把整段重发一遍。缓存命中是 1/50 价、不是零，延迟更是实打实的——实测 97 万 token 那次请求用了 **20.7 秒**。**这次没有为它加第二条阈值**（明确选了单条 80%），所以"慢"这件事现在没有任何东西在管。

**还剩两个边界**：

- **小窗口 + 保留 6 轮会抖**：窗口 32,768（表里 `qwen-max`）时阈值只有 26,214，最近 6 轮本身就超了的话，压缩完还是超——于是每轮压一次。有界（`_safe_cut` 在只剩 6 轮时返回 `None`），但每一次都是一笔要花钱的摘要调用。现在这个端点够不到，先记着。
- **超窗但没有安全切点 → 直接 400**：轮数不够 6 轮时（比如第一句就粘了一整本书）没有合法的切点，压缩帮不上忙，请求照样发出去、照样被拒。这不是这次改出来的，是压缩本身的边界。

### D9. `--api-key` / `--base-url` 可以覆盖环境变量 —— 取舍（2026-10-18）

**现在的行为**：`--model` / `--api-key` / `--base-url` 都可以在命令行临时覆盖
`providers/anthropic.py` 的默认模型和 `.env` 里的两个变量；没给就照旧读环境。

**为什么加**：临时切端点、换模型、脚本或 CI 里传不同凭据时，不必改 `.env`。

**代价**：**密钥写在命令行上会留在 shell 历史和进程列表里**（`ps` / 任务管理器看得到）。
所以帮助文本里明写"优先用 `.env`"；日常还是走环境变量，命令行只给临时/脚本场景用。程序自己
不会把 key 打印出来。

## 五、工程与测试

### E1. Windows 上有一组用例被跳过 —— 已知

- **符号链接相关 3 条**：Windows 建软链要开发者模式或管理员权限。
  - 其中两条有打桩版本兜住判断逻辑（`is_symlink` 打桩），但"真的通过软链指到别处"这条路径**从未在真机上验过**。
- **POSIX 权限位 1 条**：Windows 的权限模型和 POSIX 不是一回事，没法用同一套断言。**所以 `write_file` 的"覆盖时保留原文件权限"在 Windows 上没有验证手段。**

### E2. `uv run` 在同步失败时会返回 0 —— 工具链的坑

`.venv/Scripts/mini-code-agent.exe` 被别的进程占着时，`uv run` 的同步会失败并打印错误，但**退出码是 0**。后果是 `set -e` 拦不住，脚本会带着没跑成的验证继续往下走。

**怎么修**：验证要么用 `uv run --no-sync`（跳过同步那步），要么显式检查输出。这条已经在提交历史里害过一次（先提交后验证）。

### E3. 中间一段提交是红的，`git bisect` 跨不过去 —— 历史包袱

从"工具函数改成收 (参数字典, ToolContext)"那个提交起，接下来七个提交的测试都是红的（旧调用约定的用例没跟上），直到"把旧调用约定的用例适配过来"才回调全绿。

**后果**：拿测试做信号去 `git bisect` 那一段，会指到错误的提交。这一段之后没问题。

### E4. 没有 CI —— 已处理（2026-10-18）

`.github/workflows/ci.yml`：push / pull_request 时跑 `uv sync --frozen`、`ruff check`、`pytest`
（明确排除要花钱的真接口那组）。加 CI 能挡住 E2 那种"验证没跑成却以为跑了"的事。

### E5. 根目录的 `main.py` 和 `notebook/` 不在检查范围内 —— 取舍

它们在 `.gitignore` 里（本地试验文件，不入库），也没进 ruff/pytest 的扫描范围。这是有意的，但意味着那里面的代码没有任何保护。

### E6. Windows 重定向输出遇到非 UTF-8 编码会崩 —— 已修（2026-10-18）

**问题**：`mca "..." > out.txt` 时 Python 的 stdout 用系统 ANSI 代码页（这台机器上是 GBK），
而输出里有 `▶` / `→` / `✗`；Rich 的 legacy Windows 渲染器往 GBK 流里写会抛
`UnicodeEncodeError`。交互模式下 Python 走 Unicode 控制台 API，所以只在重定向/旧控制台出现。

**怎么修**：`console.py` 在启动时检查 `sys.stdout` / `sys.stderr` 的编码，不是 UTF-8 就
`reconfigure(encoding="utf-8", errors="replace")`。控制台本身不受影响；管道/文件从此是 UTF-8。

## 六、权限与人机协商

### F1. 权限判定认识工具的名字，加新工具靠"记得"归档 —— 中

**现在的行为**：`permissions.py` 里写着一份名单

```python
EDIT_TOOLS = ("write_file", "edit_file", "replace_lines")
```

判定（`decide_permission`）和 harness 里 `_ask` 挑哪种问法，都按这份名单分。也就是说，"权限怎么判"这个模块反过来得知道有哪些具体工具。

**为什么重要**：将来往 `default_tools()` 里加一个也会写盘的工具，只要忘了往名单里加那一行，它就在 **plan 模式下被静默放行**——而 plan 模式的全部意义就是只读。不报错、测试也不会红。

测试救不了这条：能写的测试只覆盖一半——"名单里有没有过期名字"（工具改名后）查得出来，"新工具没归进去"查不出来，因为没有任何机器可读的信号说明那个工具会不会写盘。而漏掉的方向恰好是"不安全"的那一侧。

同一份知识还写了第二处：`core/agent.py` 的 `_ask` 也是按名字判"给用户看 diff 还是看命令行"。

**怎么修**：把"类别"变成工具自己的必填声明，策略只认类别、不认名字。

- `Tool` 加一个**必填**字段（`kind: Literal["read", "edit", "shell"]` 之类），`default_tools()` 装配时逐个声明
- 注册表提供 `kind_of(name)`；harness 构造 `PermissionRequest` 时带上类别
- `permissions.py` 只剩 `(类别, 档位) → allow / deny / ask` 这张表，一个工具名都不认识

**关键在那个字段必填**：带默认值就等于把名单换了个地方写，还是靠记得；必填的话，注册一个没归类的工具会当场报错——"记得"这件事就不存在了。要动的地方：`tools/base.py`、`tools/registry.py`、`core/agent.py`、`permissions.py`，加上几个测试文件。

### F2. plan 档下 bash 仍然是"问"而不是"拒" —— 取舍（已定：维持现状）

**现在的行为**：四档管的是"改文件的工具要不要一个个问"，bash 在 `default` / `accept edits` / `plan` 下都要用户确认。所以在 `plan`（只读）档下，模型照样可以请求跑 `echo KEY=x > .env`，用户点了同意就跑成了。

**为什么重要**：plan 的承诺是"只读，先讲清楚再执行"。而 bash 能改项目里的任何文件、绕过文件工具的全部闸门（见 A1），所以只要用户点头，plan 的只读承诺就是空的。这不算 bug——用户确实看过那条命令才点的头——但"plan 等于只读"这句话在文档和界面上都不能这么说。

**已定：维持现状**——plan 下 bash 仍然问，不直接拒。理由是不想把"计划阶段跑 `git status`、`pytest --collect-only` 这类只读命令"一起堵死；靠拒掉 bash 来兑现"只读"，代价是计划阶段什么都查不了。

**代价，以及配套**：于是"plan = 只读"实际靠的是**模型自己只用读命令**——那是引导，不是强制。配套已经写在那儿了：`system_prompt.py` 的 `_MODE_HINTS["plan"]` 里明说了"只用读类工具和只读命令……不要请求会改动任何东西的命令"（那句要有个默认 system prompt 才发得出去，而 D2 2026-10-12 已修）。界面上也没说错——`/permission_mode` 报 plan 时印的是"只读：改文件直接拒（bash 仍然要问）"。被否掉的那条路是 plan 下直接拒 bash；真要做"只读命令白名单"，那是另一摊工作，而且白名单本身是启发式、会漏。

**子 agent 那边同理**：plan 档下派出的 `general-purpose` 子 agent 继承这一档，所以 `bash` 在它手里照样是"问"——见 H6。

### F3. 改文件的确认没有真 diff —— 取舍

**现在的行为**：`prompting.py` 只渲染 `PermissionRequest` 里带的东西，**不看磁盘**。于是：

- `edit_file` 给出的 `- 旧 / + 新` 是真的
- `replace_lines` 只显示"第 a-b 行换成什么"，看不到被换掉的那几行原来什么样
- `write_file` 只能说"整篇 N 行"，说不出这是新建还是覆盖

**为什么重要**：审批有多大用，取决于用户看到的够不够判断。"整篇 40 行"和"整篇 40 行，前 3 行跟现在不一样"是两码事——尤其覆盖一个已存在的文件时。

**怎么修**：把询问挪进 `_commit_change`——写完临时文件之后、`os.replace` 之前问。那一刻临时文件里就是新内容、目标文件还是旧的，diff 是现成的；而且用户犹豫的时候磁盘上什么都没变（拒绝就把临时文件删掉），跟已有的原子顶替、改前备份正好接得上。代价是改文件的工具从纯函数变成会交互的东西，只能靠注入 prompter 来测。分工也要跟着变：harness 那层只判"要不要问"，"问什么"交给工具自己。

### F4. `bypass permissions` 把用户整个从回路里拿掉 —— 取舍

**现在的行为**：四档里的 `bypass permissions` 什么都不问——改文件不问，跑命令也不问。判定（`decide_permission`）在这一档最先短路，直接返回 allow。

**为什么重要**：它是唯一一档让安全模型从"沙箱 + 人在回路"退化成"只有沙箱"的。开着的那段时间：

- 模型跑命令不再经过用户，而命令能改项目里任何文件、绕过文件工具的全部闸门（A1），并且**不留备份**——`.agent/.history` 只在文件工具那条路上写
- 命令的输出照样进模型上下文，所以 `.env` 能被读走（A2），唯一拦着的是关键词涂黑那个启发式（A3，而 A3 自己写着"不是边界"）

好在这个项目的沙箱是真沙箱（`--network none`、只读根、`.git` 只读挂载、cap-drop、非 root、跑完就删），爆炸半径是**项目目录**而不是宿主机——这正是这一档能存在的理由。

**怎么管的**：只能从命令行显式开（`--permission_mode bypass`），启动时打一行红字提示。另外它放行的只是"要不要问"，工具自己的闸门（围栏、符号链接、敏感路径、读-before-写、改前备份）照旧生效：权限不是授权。

**会话里换档（2026-10-12 起）**：交互循环里可以用 `/permission_mode [档位]` 换档，但**只放开了另外三档**——`bypass permissions` 仍然只能从命令行开，命令里给这一档会被拒掉，就是上面那条"不能从会话里切进去"的落实。另外三档能换，是因为它们要么是收紧（`plan`、`default`），要么换的是"改文件问不问"而不是"问这一层整个关掉"（`accept edits`）；每一档换下去都把这一档意味着什么打在屏幕上，不静默生效。

**代价：落盘的 meta 还是启动那一档。** `--continue` 接上来时打的那行"上次档位 X"说的是这次会话**开始时**的档，不是结束时的。想改就得往 transcript 里加一种"换档"行、`load` 跟着认——那比换档本身大，先不做。

### F5. 以 `/` 开头的一律当命令，拿它开头的路径也会被拦下 —— 取舍

**现在的行为**：交互循环里，以 `/` 开头的那一行不进模型，先过命令表。表里没有就地报一句"没有这个命令（这一行没有发给模型）"。于是 `/Users/foo/bar.py 报错了` 这种**拿绝对路径开头**的话也被拦下，用户得去掉斜杠重发一次。

**为什么重要**：另一种做法（认不出来就当普通输入递给模型）看起来更宽容，实际更糟——`/hlep` 打错一个字，模型多半会顺着答，用户还以为命令生效了；而它答的那一轮还占了历史。**以 `/` 开头是命名空间的全部约定**，这条约定简单到不用记。代价只落在"以斜杠开头的那句话"上，而且报错里明说了没发出去，不会让人等一个不存在的回答。

**怎么修**：真嫌烦就把约定收紧成"`/` 后面紧跟已知命令名才算"，其余照常递给模型。那是把上面那段权衡反过来选，不是修 bug。

## 七、工具结果的限额与落盘（2026-10-14）

### G1. 限额分三档，落盘只给两个工具 —— 取舍

**现在的行为**：`safety.py` 里三个数各管一摊——`MAX_TEXT_CHARS = 20000` 是**通用**档（系统提示词里的 AGENTS.md、权限确认里的 diff 也用它），`MAX_READ_FILE_CHARS = 50000` 给读文件的几个，`MAX_TOOL_CHARS = 5000` 给其余工具；`PREVIEW_CHARS = 1500` 是落盘之后正文里留多少。

**为什么是三个数而不是一个**：

- **通用档不能动。** 它被三类调用方共用（工具结果、系统提示词、权限确认），改它会连带把 `AGENTS.md` 截短、把用户批准前看到的 diff 截短——那两处各有各的尺度。所以工具那两档是**显式传进去**的，不是改默认值。
- **读文件那一档宽**：文件是模型要去改的东西，截在中间它就得再跑一次工具；而且 `read_file` 自带 `start_line` / `end_line`，宽不代表一定会读满。
- **其余工具那一档紧**：它们大多是"先看个大概"（列目录、搜内容、取网页），真要更多，换个更窄的问法比塞一整条进上下文划算。

**执行时的落盘（`tools/spill.py`）只挂在 `bash` 和 `web_fetch` 上**，这两个是"输出取不回来"的那一类：命令有副作用、网页下一刻会变、取一次要花钱——截掉了就是真没了。别的工具不落：`read_file` 的内容本来就是盘上那个文件（`start_line` / `end_line` 能读回来，而且**读了会记 `read_state`**，读落盘的副本反而会把那条线掐断）；`glob` / `grep` / `list_files` 重跑一次很便宜。

**折叠时还有第二道**（见 D5）：`bash` / `web_fetch` / `web_search` 标了 `Tool.fold_persist`，旧结果被折掉之前会先按 `tool_use_id` 落一份。文件已经存在就不写——折叠会反复重算，不能每算一次就重写一遍。

**落盘的位置是 `.agent/tool-results/<会话 id>/`**，和长期记忆、skill 一样在 `.agent` 底下——那里在沙箱里是**只读挂载**，模型自己的 bash 改不动它。分会话子目录是为了"删会话时一起端掉"（`--delete` 干的），也省了另外记一本"哪几个文件是哪次会话的"账。

代价是文件工具也读不了（`.agent` 是敏感目录），所以另开了一道门 `read_tool_result`（在 `files.py` 里，和 `read_memory` / `read_skill` 一个形状）。它**按名字搜**（搜遍各会话目录 + 根下平铺的），因为模型手上只有引用消息里给的那个名字、不知道也不该知道那属于哪次会话；围栏开在整个 `tool-results/` 上，所以 `--resume` 接上来的会话照样取得回自己历史里引用的那些文件。

它是**唯一一个不判 `available` 的**：落盘发生在**这一轮之内**，而工具表一轮只算一次（`runagent` 开头），按"盘上有没有落盘文件"来判的话，模型在这一轮里刚拿到路径、却调不出那个工具。

**三条定下来的**：

- **涂黑在落盘之前。** 落盘落的是 `_format` 吐出来的那份（已经过 `redact_sensitive`）。落原文等于给涂黑开个后门——文件躺在盘上，模型随时能用 `read_tool_result` 读回来。这条有测试盯着（`test_shell.py::test_the_spilled_copy_is_redacted_too`）。折叠那一路落的是历史里的正文，同样已经涂黑过。
- **落盘失败退回截断**，不是原样放进上下文。盘满、权限不对的时候，几 MB 的文本照样得截——那正是这个机制要防的事。
- **工具表是请求前缀的一部分**，所以 `read_tool_result` 挂在表尾。往末尾追加不影响前面那些的缓存，插在中间会让整个前缀作废（自动前缀缓存按前缀命中）。

**代价**：`bash` 每条流最多留 2 MiB（`MAX_CAPTURED_BYTES`），留下的一律进内存。这是从原来的 8000 字节抬上来的，配套的就是"超了落盘"——否则 2 MiB 会直接进上下文。连 2 MiB 都留不住的（几条流合计几 MB），丢掉的部分落盘也救不回来，`_format` 会明说丢了多少。

### G2. 落盘只在删会话时清，没有自动清理 —— 低

**现在的行为**：落盘文件按会话分目录（`.agent/tool-results/<会话 id>/`），`mca --delete` 删会话时连同那个目录一起端掉。除此之外不自动清：没被删的会话，它的落盘文件就一直留着。

**为什么现在还行**：它在 `.gitignore` 里，也在 `EXCLUDED_DIRS` 里（不会进模型的视野），单条上限 2 MiB，而一个会话里超限的工具结果不会有几条。分目录之后"哪几个文件是哪次会话的"不用另记——目录名就是。

**还剩两样**：

- **根下那批平铺的老文件没有主人。** 它们是按会话分目录之前留下的，`--delete` 认不出是谁的（那个会话的 id 对不上任何东西）。只能手工删一次，或者等下面那个"扫孤儿"的动作。
- **没被删的会话会一直攒着**，那是 D6 那一摊（会话本身没有批量或按时间的清理）。

**怎么修**：加一个"扫孤儿"的动作——把 `tool-results/` 下**没有对应会话文件**的子目录、以及根下那批平铺的文件列出来（先只列，删要人点头）。它比按时间删更安全，因为判据是"引用它的东西还在不在"，而不是"它有多老"。要再往上，就是给会话本身按时间清理（见 D6）。

### G3. `project_tree` 的两道闸会一起响，说明只留得住一条 —— 低

**现在的行为**：条目数到了 `MAX_TREE_NODES` 会加一句说明，字符数超了 `MAX_TOOL_CHARS` 也会加一句（`truncate_text` 的说明挂在**末尾**）。两条一起响的时候，末尾那句会被字符那道的说明连同树尾一起截掉，所以条目数那句被挪到了**树前面**。

**代价**：树不再从第一行开始（多了一行说明和一个空行）。换来的是"树本身就不全"这件事在截断之后仍然看得见——它比"显示不下"更该让模型知道。

**还剩什么**：两道闸都响时，模型只看到一句"条目数到了上限"，看不到树尾那些。要更准就得在按层挑节点的时候同时记字符预算，那样两句能合成一句准确的话（"到 1000 条 / 5000 字符为止"）。代码会复杂一些，先不做。

## 八、子 agent（2026-10-16）

主 agent 可以派一个**子 agent**去做一件事，只把结论拿回来（`core/subagent.py`）。三种类型、
三种工具池：`general-purpose` 能动手，`explore` / `plan` 只能读。工具叫 `agent`，在 CLI 层
装进注册表——和 `ask_user` 一样，是 harness 才有的能力，不在 `default_tools()` 里。

### H1. 子 agent 的上下文是一次性的，主 agent 只拿到一段总结 —— 取舍

**现在的行为**：子 agent 从零开始（看不到主 agent 和用户的对话，只有 `prompt` 那一段），
跑完之后它的整段上下文**丢掉**，主 agent 只收到"一行过程 + 它最后那段文本"。

**为什么这么定**：这是这个机制存在的**唯一理由**。主 agent 为了回答一个问题读 20 个文件，
那 20 个文件就永远留在它的上下文里、后面每一发都要重发；子 agent 读完之后只交回一段结论。
**省的是上下文，不是钱**——子 agent 每一步都是另外的请求，而且它有自己的系统提示词和工具表，
跟主 agent 不共享缓存前缀（见 H2）。

**代价**：主 agent 拿不到中间过程。子 agent 要是总结得含糊（"在某个文件里"），主 agent 就得
自己重查一遍，那一趟白派了。所以系统提示词里专门写了"报告里写清路径和行号""结论要写全，
别写『见上面』"。

**怎么修**：没什么可修的，这就是这个机制的形状。嫌不够就调提示词，别改机制。

### H2. 子 agent 不共享主 agent 的缓存前缀 —— 取舍（成本）

**现在的行为**：子 agent 的请求 = 它自己的系统提示词 + 它自己那份工具表 + 它自己的历史。
前两样和主 agent 完全不同，所以那边缓存省下的钱一点也沾不上：**它第一发按原价算**，从第二发
起才命中它自己的缓存（`runagent` 只追加，那个前提在子 agent 里照样成立）。

**一个反过来的好事**：同一轮里连着起两个**同类型**的子 agent，只要期间 git 状态没变，
`project_context` 那几段就一致（见 `system_prompt.py`），第二个的首发能在公共前缀上命中。
有个变量——那几段里最勤变的就是 git 状态，所以这个复用时有时无。

**代价**：一次 `explore` 大约 3~6 发，第一发全价。跟主 agent 自己去读同样多的文件比，**它更
贵**；换回来的是主 agent 的上下文长度。

**例外是 `fork` 类型**（`--fork` 打开时才可用）：它复用父 agent 的 system、工具表和历史，第一发
基本只付命中价。见 H8。

### H3. `Grants` 两份共用，所以批过的文件子 agent 也不再问 —— 取舍

**现在的行为**：主 agent 和子 agent 共用同一个 `Grants`。主 agent 批过某个文件之后，子 agent
写**同一个文件**不会重新问；反过来也一样。

**为什么这么定**：`Grants` 本来就是**会话级、按 (工具, 文件路径)** 记的（`permissions.py` 的
`_grant_key`）——用户批的是"这个文件、这次会话"，不是"谁去动它"。各记各的后果是同一个文件
被问两遍；重复问落在安全的那一侧，但很烦。

**代价要说清**：用户当初在主 agent 那儿看到的那处 diff，和子 agent 要写的内容**可能完全
不同**，而这个豁免是无声扩过去的。所以权限提示必须带出**来源标记**（`_LabeledPrompter`
打的那行 `（[explore] 子 agent 请求：）`）——不带的话，用户根本分不清"本会话别再问"批给了
谁、批的是什么。

**怎么修**：真嫌宽就改成子 agent 各记一份 Grants，代价是同一个文件被问两遍。

### H4. 子 agent 改动过的文件，会让主 agent 被迫重读 —— 取舍

**现在的行为**：子 agent 的 `ToolContext` 是嵌套 `runagent` 自己建的，所以它的 `read_state`
天然是空的——**它读过的文件不会替主 agent 挣到"可以改"的资格**（这条是好的）。

**反方向**：`general-purpose` 子 agent **写**过 `src/a.py` 之后，主 agent 如果之前读过它，
下次改会被 `StaleReadError` 拦住、得重读一遍。

**为什么这是对的**：文件确实变了，手上那份内容已经过期。拦住而不是静默覆盖，正是那套
读-before-写要干的事。

**代价**：用户会看到主 agent 忽然重读一批文件——那不是 bug。子 agent 动得越多，这种重读越多。

**fork 是这条的一个变体**：它进来时拿的是父 agent `read_state` 的**副本**（所以父读过的文件
它可以直接改），跑完之后一条记录都不回流——上面两个方向在它这儿仍然成立。见 H8。

### H5. 没有嵌套：子 agent 不能再派子 agent —— 取舍

**现在的行为**：子 agent 的工具池里没有 `agent`（也没有 `ask_user`、没有 `remember`）。

**这条为什么是结构性的**：`agent` 和 `ask_user` 都是在 CLI 层 `registry.register()` 注入的，
不来自 `default_tools()`，而池子是从 `default_tools()` 现筛一份**新的**——两者根本不相干。
所以要显式排除的只有 `remember` 一个。

**代价**：这个保证靠"**新增工具一律进 `default_tools()`**"这条隐含约定撑着。谁哪天在别处
注册一个新工具、又忘了想这件事，护栏就漏了。所以 `tests/test_subagent.py` 里有一条专门守它
（"三个池子里都没有 `agent`"）——那是唯一的护栏。

**为什么不做递归**：深度不可控，成本也不可控（每层第一发全价，见 H2）。真需要就手工分两步派。

**`fork` 是另一套护栏**：它不是工具池里的一个工具，而是 `agent` 的 `type` 枚举里的一项。
枚举是静态的（跟着工具 schema 一起进缓存前缀），所以**不能靠"关掉时把这一项删掉"**——那会让
工具表变、缓存当场作废。运行时由 `ctx.fork` 判能不能用、由 `depth` 判能不能再往下 fork。
见 H8。

### H6. plan 档下的 `general-purpose` 子 agent **并没有**被锁成只读 —— 已处理（只在文字里拦）

**现在的行为**：子 agent **继承**主 agent 当前那一档。所以 plan 档下派出的 `general-purpose`
和同一档下的主 agent 处境完全一样：

- 改文件那三个（`write_file` / `edit_file` / `replace_lines`）被闸门 **deny**；
- **`bash` 是 ask，不是 deny**——跟 F2 记的是同一件事。用户点头，它照样能跑命令，而命令能
  改项目里任何文件、绕过文件工具的全部闸门（见 A1）。

**所以它和 `explore` 不是一回事，别混。** `explore` / `plan` 是**池子里压根没有** bash
（`bash` 标的是 `read_only=False`，筛掉了——硬性的，没有绕过的余地）；`general-purpose`
是**用户得自己拦**。这是两种不同性质的"不能"。

**为什么不做机制上的限制**：`type` 的枚举写死在 schema 里（`Tool.params` 不随 `ctx` 变），
收不窄。改成按档位动态生成工具表是另一摊事——而且工具表一变，主 agent 的缓存前缀当场作废。

**代价**：模型要是不认账、反复试写文件，会一路吃 deny 直到把步数烧完（**这一步才是"白烧
步数"**，不是"它只能读"）。

**怎么处理的**：在 `agent` 工具的说明里明写"**plan 档下只用 `explore` 或 `plan`**"，
测试里有一条盯着那句话还在（`test_the_description_warns_about_plan_mode`）。加上
`_LabeledPrompter` 打的那行来源标记，用户至少看得出这条确认来自子 agent——但**"同意"在
plan 档下意味着什么，得他自己知道**。

### H7. 子 agent 的总结落盘，但它自己不落盘 —— 取舍

**现在的行为**：子 agent 的**对话**不落盘（它是主 agent 的一次工具调用，主 agent 的会话流水
里记着那次调用的参数和结果）；但它**交回来的那段总结**如果太长，会走 `spill` 落盘到
`.agent/tool-results/<会话 id>/`，上下文里只留预览 + id。

**为什么总结要封顶**：不封的话，一段很长的总结会原样进主 agent 的上下文，把"只把结论拿回来"
这个初衷反过来打脸。落盘而不是截断：那一段是真结论，截掉了主 agent 就只能重派一次。

**为什么子 agent 自己的对话不落盘**：它没有会话 id，也没有"接上它"这回事——它是**一次**
调用，跑完就没了。

**一条顺序上的讲究**：交回给主 agent 的字符串里，**"一行过程"在最前面**，总结在后。因为
下面还要过那道长度闸（落盘预览只留开头），放末尾的话它会被连同正文一起切掉——`project_tree`
踩过同一个坑（见 G3）。

### H8. fork 继承父 agent 的缓存前缀 —— 取舍（2026-10-18）

**现在的行为**：`fork` 是 `agent` 的 `type` 枚举里的一项（和 `explore` / `plan` /
`general-purpose` 同级），`--fork` 打开时才可用。它把父 agent 的 system prompt、工具表、
以及除最后一条 assistant 消息之外的全部历史原样带过去，再加一条任务消息。相对父 agent 上一步
发出去的请求（那正好是 `messages[:-1]`），这是**纯追加**，所以自动前缀缓存整段命中——普通子
agent 第一发全价，fork 第一发基本只付命中价。

**为什么不做成独立工具**：模型要在同一个 `type` 里挑"这次带不带上下文"，而不是先决定用哪个
工具再决定类型。代价是枚举必须静态：`--fork` 关着时 `fork` 仍在枚举里（删掉会让工具表变、
缓存作废），调用时由 `ctx.fork is None` 回一句"没打开"。

**为什么丢最后一条 assistant 消息**：fork 是在那条消息里的 `tool_use` 派发时跑的，那条消息
带着派发中的调用本身，还可能并排放着别的 `tool_use`。保留它就得给每个 `tool_use` 补结果，而
fork 的结果此刻还不存在——请求不合法。整条去掉是唯一合法且不破坏前缀的做法（它是上一发的
**响应**，本来就不在请求前缀里）。

**三条硬约束**（各有一条测试守着）：

1. **`system` 原样传，不重拼**——`build_system_prompt` 会重读 git 和记忆索引，重拼出来一定
   不是同一份前缀。
2. **工具表传父 agent 算好的那份快照**（`runagent(tool_schemas=...)`）——重算的话
   `read_memory` / `read_skill` 那类现读盘的判据可能已经变了（同一轮里刚 `remember` 过）。
3. **`agent` 工具一直挂在表上、`fork` 一直在枚举里**，递归靠运行时的 `depth` 挡——把 `fork`
   从枚举里删掉会改工具表前缀，缓存就废了。

**代价**：

- **同一批并行调用看不到**：整条 assistant 消息被丢掉，同一批里其它 `tool_use` 及其结果 fork
  都看不见。工具说明和系统提示里因此劝模型别并排调。
- **`read_state` 是副本**：fork 继承父 agent 读到过什么（父读过的文件它可以直接改），但它的
  读写只落在副本上——它读的文件不替父 agent 挣到"可以改"的资格，它改的文件会让父 agent 下次
  改之前被要求重读（H4 那条护栏仍然成立）。
- **fork 里还能调 `agent`**：它用的是父 agent 的注册表，所以 `agent` / `ask_user` 都在。
  `type="fork"` 会再开一层自己的上下文，但深度判断会拒掉它；别的类型会带自己的池子跑。
  `ask_user` 问的时候带 `[fork]` 标签。
- **第一发仍是整段上下文**：命中价只是便宜，不是免费；它之后每一步都是自己的请求。


## 九、后台子 agent（2026-10-18）

### I1. 交接只发生在两发请求之间 —— 取舍

**现在的行为**：`agent` 调用跑满两分钟（`BACKGROUND_AFTER_SECONDS`）之后，`runagent` 在
**下一发请求之前**把剩下的循环体交给 `TaskManager` 起线程继续跑，自己立刻返回任务 id。
模型主动要 `run_in_background=true` 时，交接点是第 0 步——一发请求都不先发。

**为什么不在"第一秒就丢进线程"**：超时那一刻工作线程可能正卡在 `typer.prompt` 里等权限
输入，而主线程已经回到 REPL 的 `> ` 提示符——两个线程同时读 stdin。而且交接可能落在一条
长 `bash` 的中间，那条命令既没法交接也没法取消。放在两发之间，`messages` 一定以一条完整的
`tool_result`（或最初的任务）结尾，后台接着发不会留下悬空的 `tool_use`。

**代价**：一次很长的工具调用会让"两分钟"这个数不准——正在执行的命令跑完才会交接。有意为之：
正在跑的东西不该被半路甩掉。

### I2. 后台任务的权限请求走队列，由读键盘线程问 —— 取舍（2026-10-18）

**现在的行为**：交接之后 prompter 换成 `BrokerPrompter`：`confirm_tool` / `confirm_edit` 把请求
放进 `interaction.PermissionBroker`，然后等；读键盘线程在**持有终端**时取出来，用前台同一份
`TerminalPrompter` 问用户，答案交回后台线程。**本会话 `Grants` 里已经批过的文件仍然直接放行**
（`_gate` 先查 `covers`，走不到 prompter）。

**为什么不能直接在后台线程问**：stdin 只有一个，`input()` 进去就不可中断；两个线程同时读，
提示会串、答案会错位。谁读键盘、什么时候读，见 I8。

**什么时候退回拒绝**：没有 broker 的运行（一次性模式、没注入 broker 的测试）用的是
`BackgroundPrompter`，需要批准的一律拒绝。后台的 `ask_user`（选择题）在任何情况下都不行——
fork 可能碰到，会收到一条错误结果。

**代价**：用户闲着的时候，后台任务会停在"等授权"上（见 I8）。这比"悄悄拒掉"好——至少它
能等到人回来，而不是把活干成半截。

### I3. 完成通知有两条投递路径 —— 设计

**现在的行为**：

1. 主 agent **每一发请求之前**问一次任务表（`runagent(notices=...)`）。有完成的就纯追加一条
   user 消息——不碰前面的任何一条，前缀缓存照旧；如果主 agent 正在一轮里，它这一步就能看见。
2. 如果主 agent 已经收尾、循环停在提示符上，`TaskManager.on_finish` 会往 `_chat` 的事件队列
   里放一条，把循环叫醒，跑一个**只汇报、不干活**的短回合，让模型自己开口告诉用户。

两条路靠 `take_notices()` 的"取走即标记"互斥：同一条结果只会被一边拿到，不会说两遍。

**为什么不能只做第 1 条**：用户要的是模型主动开口。停在提示符上时没有"下一发请求"，只靠
`notices` 就得等用户再敲一句话。

**代价**：`_chat` 的输入从"主线程阻塞读"变成了"读键盘线程 + 事件队列"。`idle` 事件保证只有
主循环空闲时才打印 `> `；队列空了才 `idle.set()`，避免重复提示符。

### I4. 汇报回合多花一次请求 —— 取舍

**现在的行为**：每完成一个后台任务，模型多被调用一次（`max_steps=1`，同一份 system / 工具
表 / 历史，只追加一条 user 消息）。

**为什么**：这是"模型主动告知"的代价。它和上一发共享前缀，通常按缓存命中价算，但不是零。

**怎么减少它**：主 agent 正在跑一轮时，结果会通过 `notices` 并进那一步，汇报回合就不会再
触发（`take_notices` 返回空）。所以只有"后台任务在用户闲置时完成"这一种情况才多这一发。

### I5. 并发上限是软上限 —— 取舍

**现在的行为**：模型主动要后台时，`TaskManager.running() >= BACKGROUND_LIMIT`（2）就拒绝，
回一句"先做别的或用同步 agent"。**自动交接不受这个限制**——它本来就已经在跑了，拦下来只会
把它卡在前台。

**代价**：极端情况下可能同时有三个后台任务（一个自动交接 + 两个主动要的）。真正兜底的是
预算：每个任务都有自己的 `max_steps`。

### I6. 后台任务是进程内的 —— 问题（有意接受）

**现在的行为**：任务表在内存里，工作线程是 daemon。进程退出（`/exit`、Ctrl+C、崩溃）时它们
被硬杀，结论一起丢。`--resume` 接上来的会话里，历史中的任务 id 是死的。

**为什么可以接受**：v1 的后台任务主要做只读的查证/分析，没有副作用；写操作又受到 I2 的限制，
最多留下一份已经写完的文件，不会留下半截。真正的持久化要另做一套（把任务过程也落盘、启动时
恢复），那是另一摊。

**怎么让用户有数**：`/tasks` 列出在跑什么、跑了多久；`/status` 报"还有几个在跑"；`/tasks
cancel` 让它在下一步之前停下（正在跑的命令不会被硬杀，见 I1）。

### I7. 工具 schema 变了一次 —— 已处理（一次性的）

`agent` 的 schema 多了 `run_in_background` 字段，属于工具表的一部分。升级后每个会话的**第一发
请求**要重建前缀缓存，按原价算；之后照旧只追加。

### I8. 后台授权只在提示符边界处理 —— 取舍（2026-10-18）

**现在的行为**：读键盘线程每次拿到终端控制权时先清一遍授权队列——打印 `> ` 之前，以及用户
敲完一行、还没把这行交给主循环之前。用的渲染和读法就是前台的 `TerminalPrompter`：预览、y/n/a、
拒绝理由完全一致。`Grants` 只在 `allowed and remember` 且任务没被取消时记。

**为什么是这两个边界**：`typer.prompt` 一旦进去就不可中断，而 stdin 只有一个读者。把提问放在
这两个点上，读键盘线程是唯一的读者，主循环要么正阻塞在 `events.get()`、要么在跑一轮（那时它
不读 stdin，`report_background` 用 `NullPrompter`）。

**用户会看到什么**：

- 请求如果是在读键盘线程**空闲等待**时到的，`on_defer` 会叫醒主循环打一句"后台任务在等授权；
  按回车后处理"，读键盘线程立刻问，不需要额外回车。
- 用户正停在 `> ` 上时，请求会等下一次回车；那一行会先被读走，然后才问授权。所以可能出现
  "我敲了一句、它先问我一个权限问题、再处理我那句话"。
- 多个请求按到达顺序逐个问；全部答完才回到 `> `。

**代价**：提示语可能和 `> ` 挤在同一行（行输入终端的限制）；用户完全没在终端前时，后台任务
会一直等（没有超时——等授权本来就要有人在）。退出时未答的请求按拒绝收尾，还在跑的任务由
`_chat` 的 `finally` 里 `TaskManager.cancel_all()` 停下。


## 十、工具批内并行（2026-10-18）

### J1. 只读工具按段并行，不可并行的调用是屏障 —— 设计

**现在的行为**：`runagent` 把一批 tool_use 按原顺序切成若干段——连续的可并行调用
（`Tool.read_only`）算一段，每个不可并行的调用单独算一段。段与段串行，段内用 daemon 线程 +
`Semaphore(4)` 并行。结果列表和 trace 仍按原顺序拼。

**谁能并行**：`read_file` / `grep` / `glob` / `list_files` / `project_tree` / `read_memory` /
`read_skill` / `read_skill_file` / `read_tool_result` / `web_search` / `web_fetch`。
`write_file` / `edit_file` / `replace_lines` / `bash` / `remember` / `echo` / `ask_user` /
`agent` 都是屏障。

**为什么按段，而不是"读的并行、写的同时串行"**：模型给出的顺序有隐含语义——排在一个写之后
的读，串行执行时要看到那个写的结果。跨过写去并行会让"读到的到底是写之前还是写之后"变得不
确定。切段是对原串行顺序的合法重排：每段开始时，前面所有调用都已经结束。

**为什么不干脆整批串行**：相邻的只读调用确实互不依赖，尤其 `web_search` / `web_fetch` 是
秒级的；这是墙钟时间的主要来源。

**代价**：

- 被写隔开的两个读不会并行。
- 并行段里所有 `→` 行先出现，`←` 行按原顺序后出现；这是并行在终端上的样子。
- 一个慢调用会压住同段里快调用的**结果展示**（执行没有被压住）。
- web 工具并行会同时花钱，也可能撞 Tavily 的限流；并发上限是 4。
- 用线程不用 asyncio（工具都是 I/O 密集型）；批内不取消，取消在批与批之间处理。

**线程安全**：worker 只执行、不打印，输出由主线程在 join 后按顺序打。只读工具里只有
`read_file` 会改共享的 `read_state`——并发写的是 dict 的单键赋值，CPython 下是原子的；而写
文件的守卫只在串行段里跑，不会和它同时发生。`web_fetch` 的落盘用 `tool_use_id` 当文件名 +
原子替换；`web_search` / `web_fetch` 每次调用现建客户端，没有共享 session。

**一条护栏**：测试里守着"并行集里每个工具在 default 档下 `decide_permission` 都返回 allow"。
并行段是在 worker 线程里跑 `_gate` 的，靠的就是这条——以后加一个"只读但需要问"的工具，
这条会红，逼人给它单独一个串行段或重新想并行判据。


## 十一、流式输出（2026-10-18）

### K1. 流被截断时 SDK 不抛异常，`stop_reason` 是 `None` —— 已处理

真实端点和本地假端点都复现过：服务端发到一半断开、没有 `message_stop`，SDK 正常返回一个
部分消息，`stop_reason=None`。如果照 `complete()` 的写法把它兜底成 `end_turn`，半截回答会
被当成完整答案回填进历史，而且没有任何提示。

**现在的处理**：`AnthropicProvider.stream()` 在归一化之前先看 `stop_reason is None`——没显示
过文字就抛 `TransientProviderError`（`ask()` 可以安全补一次），显示过就抛普通
`ProviderError`（补一次会把已经打出来的字再打一遍）。

### K2. 显示过正文之后不自动重试 —— 取舍

`ask()` 对瞬时故障补一次，前提是这一发还没产生可见输出。流式路径把"字已经上了屏幕"当成
既成事实：中途 `error` 事件或连接断开时，provider 把瞬时错误降级成普通的 `ProviderError`，
上层不再重发。用户看到的是不完整的内容 + 一句"再发一次"。

**为什么不再试**：重发要么从头再打一遍（前缀重复），要么先清屏（终端不一定支持）。两条都
比"停下来让人决定"更糟。

### K3. 流式的 `max_tokens` 直接从天花板起步 —— 取舍

非流式撞上 `max_tokens` 会抬到 16384 重发一次，原因是那一发还没给用户看过，重发只是多花
一次生成的钱。流式不能这么做：文字已经显示了，重发就是重复输出。

**现在的处理**：流式请求一开始就 `max_tokens=max(self.max_tokens, self.ceiling)`。
`max_tokens` 是上限不是目标，写大了不额外花钱；真撞上天花板说明这次回答确实放不下，
`stop_reason` 会照实带回 `max_tokens`。

### K4. 后台任务、子 agent 和压缩摘要不流式 —— 取舍

它们和前台共用同一个终端：后台任务实时打字会和用户正在输入的行、权限提示搅在一起；
压缩摘要本来就不给人看。**只有前台主 agent 的那一发**会走 `stream()`，其余仍然 `complete()`。

### K5. 多 text 块的换行差异 —— 低

`text_stream` 把多个 text 块的 delta 直接串起来，而 `ModelResponse.text` 是用 `\n` 连接
多个块。真实端点每次只返回一个 text 块（thinking 单独一块，走单独的回调，不进正文），所以
现在看不到差异；真遇到多块时，屏幕上会少一个换行，内容本身不丢。

### K6. thinking 只在 `--show-thinking` 下显示 —— 取舍（2026-10-19）

**现在的行为**：provider 遍历原始 `content_block_delta`，把 `thinking_delta` 交给
`on_thinking`、`text_delta` 交给 `on_text`；只有显式打开 `--show-thinking`（隐含
`--stream`）才把 `on_thinking` 接到终端，样式是 dim。两者之间由 agent 自动补一个换行。

**两个"显示过"要分开**：

- 重试判据看的是**任何可见输出**——显示过 thinking 之后断流也不再自动重发，否则屏幕上会
  重复一遍推理。
- `final_streamed` 只看**正文**——显示过 thinking 不代表最终回答已经在屏幕上，轮末该打的
  正文还是要打。

**代价**：`--show-thinking` 会明显增加终端输出量；推理内容是完整的模型输出，也会随会话落盘
（和非流式路径一样，thinking block 本来就在 `assistant_content` 里）。

### K7. 等待提示只在真终端上、用 `\r` 擦除 —— 取舍（2026-10-19）

**现在的行为**：`WaitHint.begin()` 在请求发出后、第一个 token 到来前显示一行
「（等待模型输出…）」；第一个 chunk（thinking 或正文）到达时、或请求结束时擦掉。
`console.is_terminal` 为假（重定向到文件、测试捕获）时完全不显示，避免往输出里塞控制字符。

**局限**：

- 擦除靠 `\r` + 空格，是行内操作；如果提示行被别的东西（比如权限提示）打断，可能会留下
  残影。前台回合里不会并发写终端，所以正常路径没有这个问题。
- 进程在等待中被硬杀时，提示可能留在屏幕上。
- 非流式路径没有这个提示：它本来就一口气等到完整回复，加一个"等待"窗口也只是噪声。
